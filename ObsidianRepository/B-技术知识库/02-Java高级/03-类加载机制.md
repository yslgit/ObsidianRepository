### 核心概念
**类加载机制**是 JVM 将 `.class` 文件加载到内存并进行校验、转换和初始化的过程。**双亲委派模型**是 Java 推荐（而非强制）的类加载器协作方式，保证了核心类库的安全和唯一性。理解类加载机制对于掌握 Tomcat 隔离、热部署、OSGi 模块化以及解决类冲突至关重要。

### 常见误区
❌ **误区 1**：类加载只发生在 `new` 关键字时
✅ **真相**：类加载可能在访问静态字段、调用静态方法、反射、子类初始化、`new` 关键字、JVM 启动时指定的主类等多种场景触发。

❌ **误区 2**：双亲委派是 JVM 强制规范
✅ **真相**：双亲委派是 Java 推荐的实现方式，而不是强制规范。用户可以通过覆盖 `loadClass()` 方法打破它（如 Tomcat、OSGi）。

❌ **误区 3**：`public static final` 常量一定会触发初始化
✅ **真相**：如果常量在编译期已确定（编译时常量），则会被放入类的常量池，引用类不会触发初始化。只有运行时才能确定的常量才会触发。

❌ **误区 4**：同一个类加载器永远只加载一个类一次
✅ **真相**：理论上同一个类加载器对同一个类只加载一次，但热部署通过创建新的类加载器来实现"重新加载"，旧的类加载器和类可以被 GC。

### 实战建议
1. **避免类加载器泄漏**：自定义类加载器使用完后及时释放引用，防止 Metaspace OOM
2. **Maven 依赖冲突**：使用 `mvn dependency:tree` 排查类冲突，`exclusion` 排除多余依赖
3. **Tomcat 部署**：不同应用使用不同的 WebappClassLoader，同名类不冲突
4. **静态变量不跨类加载器**：不同类加载器加载的同一个类，静态变量互不共享
5. **Class.forName vs loadClass**：需要执行静态代码块时用 `forName`，仅加载用 `loadClass`
6. **JDK 9+ 模块化**：跨模块反射需在 `module-info.java` 中 `open` 或 `exports`

## 1. 类加载的生命周期

### 1.1 类加载的 7 个阶段

```
一个类的完整生命周期：

┌─────────────────────────────────────────────────────────┐
│                   加载 Loading                           │
│  ↓                                                      │
│  ┌────────────────────────────────────────────────┐     │
│  │ 连接（Linking）                                 │     │
│  │  ├── 验证 Verification                         │     │
│  │  ├── 准备 Preparation                          │     │
│  │  └── 解析 Resolution                           │     │
│  └────────────────────────────────────────────────┘     │
│  ↓                                                      │
│  初始化 Initialization                                   │
│  ↓                                                      │
│  使用 Using                                              │
│  ↓                                                      │
│  卸载 Unloading                                          │
└─────────────────────────────────────────────────────────┘

注意：验证、准备、解析统称为"连接"（Linking）
解析阶段在某些情况下可以在初始化之后开始（JVM 规范允许）
```

### 1.2 加载（Loading）

```java
// 加载阶段完成三件事：
// 1. 通过类的全限定名获取二进制字节流
// 2. 将字节流的方法区数据结构转化为方法区的运行时数据结构
// 3. 在堆中生成该类的 Class 对象，作为方法区数据的访问入口

// 二进制字节流的来源：
// - 本地文件：.class 文件（最常见）
// - JAR 包：java.util.jar
// - 网络：Applet、动态代理
// - 动态生成：Spring AOP 的 CGLIB Proxy
// - 数据库：从数据库读取类数据
// - 加密文件：自定义类加载器解密后加载

// 数组类的加载（特殊规则）：
// 数组类本身不通过类加载器创建，由 JVM 直接创建
// 数组类的元素类型（Component Type）由类加载器加载
// 比如：String[] 的加载由 Bootstrap ClassLoader 加载 String.class

// 类加载完成的标志：
// 1. 类的二进制字节流被读取到方法区（JDK 8+ 为 Metaspace）
// 2. 字节流的数据结构被转为方法区的数据结构（InstanceKlass）
// 3. 堆上生成了对应的 Class 对象
```

### 1.3 验证（Verification）

```java
// 验证是类加载最耗时的一个阶段，目的是保证字节流安全
// JVM 规范规定验证不通过抛 java.lang.VerifyError

// 四个验证阶段：

// 1️⃣ 文件格式验证（魔数、版本号等）
//    - 魔数：0xCAFEBABE（咖啡宝贝）
//    - 版本号：JDK 8 = 52.0（次版本.主版本）
//    - 常量池中是否有不被支持的常量类型
//    - 文件是否完整

// 2️⃣ 元数据验证（语义分析）
//    - 类是否有父类（除 Object 外）
//    - 父类是否允许被继承（final）
//    - 是否实现了所有抽象方法
//    - 是否覆盖了父类的 final 方法

// 3️⃣ 字节码验证（最复杂）
//    - 数据流分析：操作数栈的数据类型与指令序列配合
//    - 控制流分析：跳转指令不会跳到方法体之外
//    - 保证类型转换安全
//    - StackMapTable（JDK 7+）：每个指令执行前的栈和局部变量类型映射

// 4️⃣ 符号引用验证
//    - 符号引用中描述的全限定名是否能找到对应的类
//    - 符号引用中的字段/方法的可访问性检查（private/public 等）

// 关闭验证：-Xverify:none（JDK 13 移除，不建议关闭）
```

### 1.4 准备（Preparation）

```java
// 准备阶段：为类的静态变量分配内存并设置零值（default value）
// 注意：此时分配的是方法区中的内存（JDK 7+ 为堆中的 Class 对象关联区域）

// JDK 8 之前：static 变量在方法区（PermGen）
// JDK 8 之后：static 变量在堆中（Class 对象关联的 java.lang.Class 实例）

public class PreparationDemo {
    // 准备阶段后：
    public static int value = 123;
    // → 此时 value = 0（零值），不是 123

    // 准备阶段后：
    public static final int CONSTANT = 123;
    // → 此时 CONSTANT = 123（编译期 ConstantValue 属性自动赋值）

    public static Object obj = new Object();
    // → 准备阶段: obj = null
    // → 初始化阶段: obj = new Object()（调用 <clinit>）

    // 零值规则：
    // int → 0, long → 0L, float → 0.0f, double → 0.0d
    // boolean → false, char → ' ', reference → null
}
```

### 1.5 解析（Resolution）

```java
// 解析阶段：将常量池中的符号引用替换为直接引用

// 符号引用（Symbolic Reference）：
// 以字面量形式描述目标，与 JVM 内存布局无关
// 例如：Class 文件中 CONSTANT_Class_info、CONSTANT_Methodref_info

// 直接引用（Direct Reference）：
// 指向目标的指针、相对偏移量或句柄
// 与 JVM 内存布局直接相关

// 解析动作针对的 7 种常量类型：
// 1. 类/接口解析（CONSTANT_Class_info）
// 2. 字段解析（CONSTANT_Fieldref_info）
// 3. 方法解析（CONSTANT_Methodref_info）
// 4. 接口方法解析（CONSTANT_InterfaceMethodref_info）
// 5. 方法类型解析（CONSTANT_MethodType_info，JDK 7+）
// 6. 方法句柄解析（CONSTANT_MethodHandle_info，JDK 7+）
// 7. 调用点限定解析（CONSTANT_InvokeDynamic_info，JDK 7+）

// ⚠️ 解析的时机：
// JVM 规范允许在类初始化之后再解析（延迟解析）
// invokedynamic 指令必须在初始化后解析
// 这种灵活性是 Lambda 表达式和动态语言支持的基础
```

### 1.6 初始化（Initialization）

```java
// 初始化阶段执行类构造器 <clinit>() 方法
// <clinit>() 由编译器自动收集所有静态变量的赋值动作和静态代码块合并生成

public class InitDemo {
    public static int a = 1;           // 静态变量赋值

    static {                          // 静态代码块
        b = 2;
        // System.out.println(b);     // ❌ 编译错误：非法向前引用
    }

    public static int b = 2;           // 静态变量赋值（在后面）

    // 编译器生成的 <clinit>() 等价于：
    // static void <clinit>() {
    //     a = 1;
    //     b = 2;
    //     b = 2;            // 代码块中的赋值 + 声明时的赋值
    // }
    // 注意：静态代码块中对 b 的赋值是合法的（赋值行为），但访问（读取）不合法
}

// <clinit>() 的特点：
// 1. 线程安全：JVM 在多线程环境中会加锁同步 <clinit>() 的执行
// 2. 单次执行：一个类的 <clinit>() 只会被执行一次
// 3. 父类优先：子类的 <clinit>() 执行前，父类的 <clinit>() 已执行完毕
// 4. 非必须：如果类没有静态变量和静态代码块，不生成 <clinit>()
// 5. 接口不要求：接口的 <clinit>() 不要求父接口初始化（除非使用父接口的变量）
```

**触发初始化的 6 种场景（主动引用）：**

```java
// JVM 规范规定以下 6 种情况必须立即初始化：

// 1. new 对象
new Demo();

// 2. 访问静态字段（非编译期常量）
System.out.println(Demo.staticField);

// 3. 调用静态方法
Demo.staticMethod();

// 4. 反射
Class.forName("com.example.Demo");

// 5. 子类初始化（父类必须先初始化）
new SubDemo();

// 6. JVM 启动时指定的主类（main 方法所在类）
//    java com.example.Main
```

**不触发初始化的 5 种场景（被动引用）：**

```java
// 1. 通过子类引用父类的静态字段
//    → 只触发父类初始化，不触发子类
class Parent {
    static int value = 123;
    static { System.out.println("Parent init"); }
}
class Child extends Parent {
    static { System.out.println("Child init"); }
}
// 使用
System.out.println(Child.value);
// 输出：Parent init （Child 不初始化）

// 2. 通过数组定义引用类
//    → 数组由 JVM 直接创建，不触发类初始化
Demo[] demos = new Demo[10];
// Demo 类不会被初始化

// 3. 访问编译期常量（static final）
//    → 常量在编译期放入引用类的常量池，不会触发初始化
class Constants {
    static final String NAME = "hello";
    static { System.out.println("Constants init"); }
}
System.out.println(Constants.NAME);
// 输出：hello（Constants 不初始化）

// 4. 接口初始化不触发父接口初始化（除非使用父接口的变量）
interface A {
    int x = 1;
}
interface B extends A {
    int y = 2;
}
// B.y 被访问时，B 初始化但不要求 A 初始化
// 注意：如果访问的是 A.x（通过 B.x），则 A 必须初始化

// 5. ClassLoader.loadClass()
//    → 不会触发初始化
ClassLoader cl = Demo.class.getClassLoader();
Class<?> clazz = cl.loadClass("com.example.Demo");
// Demo <clinit>() 不会执行
```

## 2. 类加载器

### 2.1 类加载器体系

```java
// JDK 8 及之前（三层类加载器）：

// ┌──────────────────────────────────────────────────────────┐
// │  Bootstrap ClassLoader（启动类加载器）                     │
// │  └── 负责加载：$JAVA_HOME/jre/lib/rt.jar、charsets.jar 等 │
// │     （核心 JDK 类库）                                       │
// │  语言：C++ 实现（JDK 8 及以前），null（Java 中引用为 null）     │
// │  加载路径：-Xbootclasspath 指定                              │
// └──────────────────────┬───────────────────────────────────┘
//                        │ 委派
// ┌──────────────────────┴───────────────────────────────────┐
// │  Extension ClassLoader（扩展类加载器，JDK 9 改为 Platform） │
// │  └── 负责加载：$JAVA_HOME/jre/lib/ext/ 目录               │
// │  语言：Java 实现（sun.misc.Launcher$ExtClassLoader）       │
// │  父加载器：Bootstrap ClassLoader                            │
// └──────────────────────┬───────────────────────────────────┘
//                        │ 委派
// ┌──────────────────────┴───────────────────────────────────┐
// │  Application ClassLoader（应用/系统类加载器）               │
// │  └── 负责加载：classpath 下的所有类                        │
// │  语言：Java 实现（sun.misc.Launcher$AppClassLoader）       │
// │  父加载器：Extension ClassLoader                            │
// │  获取：ClassLoader.getSystemClassLoader()                  │
// └──────────────────────────────────────────────────────────┘

// JDK 9 模块化后的变化：
// - Bootstrap ClassLoader 不再加载 rt.jar，改为加载 jdk.internal 模块
// - Extension ClassLoader → Platform ClassLoader
// - 平台类不再由 Extension 加载，改为 Platform ClassLoader 管理平台模块
// - 模块化限制反射访问（跨模块需在 module-info.java 中声明）
```

### 2.2 双亲委派模型

```java
// 双亲委派模型（Parent Delegation Model）：
// 当一个类加载器收到加载请求时，先不自己加载，而是委派给父加载器
// 父加载器也重复这一过程，直到顶层的 Bootstrap ClassLoader
// 如果父加载器无法加载（找不到类），子加载器才尝试自己加载

// 源码分析（java.lang.ClassLoader）：
public abstract class ClassLoader {
    // 父类加载器
    private final ClassLoader parent;

    protected Class<?> loadClass(String name, boolean resolve)
            throws ClassNotFoundException {
        synchronized (getClassLoadingLock(name)) {
            // 1. 检查该类是否已经被加载
            Class<?> c = findLoadedClass(name);
            if (c == null) {
                try {
                    // 2. 委派给父加载器
                    if (parent != null) {
                        c = parent.loadClass(name, false);
                    } else {
                        // 没有父加载器 → Bootstrap ClassLoader
                        c = findBootstrapClassOrNull(name);
                    }
                } catch (ClassNotFoundException e) {
                    // 3. 父加载器加载失败
                    //    ClassNotFoundException 不抛出
                }

                if (c == null) {
                    // 4. 自己尝试加载
                    c = findClass(name);
                }
            }

            if (resolve) {
                resolveClass(c);  // 连接（解析）阶段
            }
            return c;
        }
    }

    // 子类覆盖此方法实现自定义类加载
    protected Class<?> findClass(String name)
            throws ClassNotFoundException {
        throw new ClassNotFoundException(name);
    }
}

// 双亲委派的目的（3 个保证）：
// 1. 安全性：防止核心 API 被篡改
//    用户写的 java.lang.String 不会被加载（Bootstrap 加载了）
// 2. 唯一性：核心类在所有类加载器中一致
//    同一个类在 JVM 中只被加载一次
// 3. 优先级：核心类优先加载
//    先让 Bootstrap 尝试，保证 JDK 类优先

// ⚠️ 全盘负责委托机制：
// 类加载器在加载一个类时，如果这个类引用了其他类
// 被引用的类也由该加载器加载（除非显式使用线程上下文类加载器）

// 类加载器的命名空间：
// 不同类加载器加载的同一个类（全限定名相同）被视为不同类
// instanceof 判断会失败
```

### 2.3 双亲委派的打破

双亲委派模型虽然是 Java 推荐的方式，但在某些场景下不得不打破。历史上出现过 3 次大规模的"破坏"。

#### 第一次破坏：向下兼容（已过时）

```java
// JDK 1.2 引入双亲委派时，为了兼容已有的用户自定义类加载器
// 在 ClassLoader 中添加了 findClass() 方法

// 如果用户覆盖 loadClass() → 不遵循双亲委派（老方式）
// 如果用户覆盖 findClass() → 遵循双亲委派（推荐方式）

// 现在几乎没人覆盖 loadClass() 了，但仍有例外（如 Tomcat）
```

#### 第二次破坏：线程上下文类加载器（SPI）

```java
// 核心问题：
// Bootstrap ClassLoader 加载了核心 SPI 接口（如 javax.sql.Driver）
// 但实现类（如 MySQL 的 com.mysql.cj.jdbc.Driver）由 Application ClassLoader 加载
// Bootstrap 无法找到 Application ClassLoader 加载的类

// 解决方案：线程上下文类加载器（Thread Context ClassLoader）
// 父加载器可以通过 Thread.currentThread().getContextClassLoader()
// 获取子加载器的引用，从而加载子加载器命名空间中的类

public class ServiceLoader<S> {
    // ServiceLoader 使用线程上下文类加载器加载 SPI 实现
    public static <S> ServiceLoader<S> load(Class<S> service) {
        ClassLoader cl = Thread.currentThread().getContextClassLoader();
        return new ServiceLoader<>(service, cl);
    }
}

// JDBC 驱动加载的经典场景（JDK 6 之后）：
// DriverManager 由 Bootstrap ClassLoader 加载
// 但 SPI 接口的实现类由 Application ClassLoader 加载

// JDK 6 之前的 JDBC：
// Class.forName("com.mysql.jdbc.Driver");  // 手动注册

// JDK 6+ 使用 ServiceLoader：
// 在 META-INF/services/java.sql.Driver 中声明实现类
// 由 DriverManager 通过 ServiceLoader 自动加载
public class DriverManager {
    static {
        loadInitialDrivers();  // 使用 ServiceLoader 加载
    }

    private static void loadInitialDrivers() {
        // 使用当前线程上下文类加载器加载 SPI 实现
        // 打破了"父加载器不能访问子加载器加载的类"的限制
        ServiceLoader<Driver> loadedDrivers =
            ServiceLoader.load(Driver.class);
        // ...
    }
}
```

#### 第三次破坏：容器和模块化

```java
// Tomcat 容器（最典型的破坏案例）：

// Tomcat 的类加载器架构：
// ┌────────────────────────────────────────────┐
// │  Bootstrap ClassLoader                     │
// └────────────┬───────────────────────────────┘
//              │
// ┌────────────┴───────────────────────────────┐
// │  Extension ClassLoader                     │
// └────────────┬───────────────────────────────┘
//              │
// ┌────────────┴───────────────────────────────┐
// │  Application ClassLoader                   │
// │  （Tomcat 自身类库）                        │
// └────────────┬───────────────────────────────┘
//              │
// ┌────────────┴───────────────────────────────┐
// │  Common ClassLoader                       │
// │  /common/*（Tomcat 和所有 Web 应用共享）     │
// └────────────┬───────────────────────────────┘
//         ┌────┴────┐
// ┌───────┴────┐ ┌──┴────────┐
// │ WebApp1    │ │ WebApp2   │
// │ ClassLoader│ │ ClassLoader│
// └────────────┘ └───────────┘

// Tomcat 为什么要破坏双亲委派？
// 1. 隔离性：两个 Web 应用可能有同名不同版本的类
//    如：不同版本的 Spring、不同版本的 MyBatis
// 2. 优先加载 Web 应用的类：WebAppClassLoader 优先加载自己 WAR 包中的类
// 3. JSP 热部署：修改 JSP 后，创建新的类加载器重新加载

// WebappClassLoader 的加载顺序（与双亲委派相反）：
// 1. 检查是否已被加载（findLoadedClass）
// 2. 优先从本 Web 应用的 /WEB-INF/classes 加载
// 3. 优先从本 Web 应用的 /WEB-INF/lib 加载
// 4. 委派给父加载器
// 注意：J2SE 核心类仍然由父加载器优先加载（避免核心类被篡改）

// OSGi（更彻底的破坏）：
// OSGi 的类加载器是"网状结构"，不是树状结构
// 每个 Bundle（模块）有自己的类加载器
// Bundle A 可以委派给 Bundle B 加载特定类
// OSGi 完全废弃了双亲委派模型
```

### 2.4 自定义类加载器

```java
// 自定义类加载器的两种方式：

// 方式 1：覆盖 findClass()（遵循双亲委派）
public class FileClassLoader extends ClassLoader {
    private final String classPath;

    public FileClassLoader(String classPath) {
        super(ClassLoader.getSystemClassLoader());  // 父为 AppClassLoader
        this.classPath = classPath;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        String fileName = classPath + File.separator
            + name.replace('.', File.separator) + ".class";

        try (FileInputStream fis = new FileInputStream(fileName);
             ByteArrayOutputStream bos = new ByteArrayOutputStream()) {

            byte[] data = new byte[1024];
            int len;
            while ((len = fis.read(data)) != -1) {
                bos.write(data, 0, len);
            }
            byte[] classBytes = bos.toByteArray();

            // defineClass 将字节数组转换为 Class 对象
            return defineClass(name, classBytes, 0, classBytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }
}

// 使用
FileClassLoader cl = new FileClassLoader("/tmp/classes");
Class<?> clazz = cl.loadClass("com.example.MyClass");
Object obj = clazz.newInstance();

// 方式 2：覆盖 loadClass()（打破双亲委派）
public class HotDeployClassLoader extends ClassLoader {
    @Override
    public Class<?> loadClass(String name, boolean resolve)
            throws ClassNotFoundException {
        synchronized (getClassLoadingLock(name)) {
            Class<?> c = findLoadedClass(name);
            if (c != null) return c;

            // 核心类还是委派给父加载器
            if (name.startsWith("java.") || name.startsWith("javax.")) {
                try {
                    c = getParent().loadClass(name);
                } catch (ClassNotFoundException e) { }
            }

            if (c == null) {
                // 非核心类自己加载（不委派）
                c = findClass(name);
            }

            if (resolve) resolveClass(c);
            return c;
        }
    }
}
```

## 3. 热部署

### 3.1 热部署原理

```java
// 热部署（Hot Deployment/Reloading）的核心思路：
// 创建一个新的类加载器来加载更新后的类文件
// 旧的类加载器和旧的类可以被 GC 回收

// ⚠️ 注意事项：
// 1. 类的全限定名不变，但由不同的类加载器加载 → 在 JVM 中是不同的类
// 2. 之前已创建的旧类的实例需要重新创建
// 3. 静态变量会丢失（被新类加载器重新初始化）
// 4. 不同类加载器加载的同一个类，互不共享 static 变量

// 热部署的限制：
// - 不能跨类加载器直接赋值（ClassCastException）
// - 需要由"基础类加载器"加载的类作为接口桥梁
// - 序列化/反序列化隔离

// 热部署实现步骤：
// 1. 监听 class 文件变化（文件时间戳）
// 2. 创建新的类加载器
// 3. 用新类加载器重新加载所有需要热替换的类
// 4. 用反射创建新的实例
// 5. 替换原有实例
```

### 3.2 简单热部署实现

```java
// 热部署核心：隔离依赖关系
// 使用"协作式"设计——基类由公共类加载器加载，实现类由子加载器加载

// 定义一个接口（由 System ClassLoader 加载）
public interface IHelloService {
    String sayHello();
}

// 实现类（由自定义类加载器加载，可以实现热部署）
public class HelloServiceImpl implements IHelloService {
    @Override
    public String sayHello() {
        return "Hello v1.0";
    }
}

// 热部署类加载器
public class HotSwapClassLoader extends ClassLoader {
    private final String classPath;

    public HotSwapClassLoader(String classPath) {
        super(ClassLoader.getSystemClassLoader());
        this.classPath = classPath;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        // 从指定路径加载 .class 文件
        // ... 实现与 FileClassLoader 类似

        // 关键：不委派给父加载器加载实现类
        // 但父加载器可以加载接口（IHelloService）
        // 所以 IHelloService 由 System ClassLoader 加载
        // HelloServiceImpl 由 HotSwapClassLoader 加载
        // 两者配合实现热部署
        return defineClass(name, classBytes, 0, classBytes.length);
    }
}

// 使用
// 1. 第一次加载
HotSwapClassLoader cl = new HotSwapClassLoader("/tmp/classes");
Class<?> clazz = cl.loadClass("com.example.HelloServiceImpl");
IHelloService service = (IHelloService) clazz.newInstance();
service.sayHello();  // "Hello v1.0"

// 2. 修改 HelloServiceImpl.java，重新编译
// 3. 重新加载
HotSwapClassLoader newCl = new HotSwapClassLoader("/tmp/classes");
Class<?> newClazz = newCl.loadClass("com.example.HelloServiceImpl");
IHelloService newService = (IHelloService) newClazz.newInstance();
newService.sayHello();  // "Hello v2.0"

// 注意：旧的 cl、clazz、service 可以被 GC
// 新的 newCl 和旧的 cl 加载的 HelloServiceImpl 在 JVM 中是两个不同的类
// 但它们都实现了 IHelloService（由 System ClassLoader 加载的同一个接口）
// 所以类型转换成功
```

### 3.3 热部署框架对比

```java
// ┌────────────┬──────────────┬──────────────────┬───────────────┐
// │ 框架        │ 实现方式     │ 优点              │ 缺点           │
```

```java
// JDK 9 引入了模块化系统（JPMS），类加载器体系也发生了变化：

module com.example.core {

// 未开放的包：
// - 非导出包：外部无法 import
// - 非开放包：外部无法通过反射访问（setAccessible 失效）

// JDK 9+ 的关键参数：
// --add-opens java.base/java.lang=ALL-UNNAMED
//   开放 java.base/java.lang 包给所有未命名模块
//   常用于解决旧框架的反射访问问题
```

```java
// 1. 该类的所有实例都被 GC
```

## 6. 面试题

### Q1：Class.forName 和 ClassLoader.loadClass 的区别？

```java
// 核心区别：

// Class.forName()：
// 1. 默认执行类的初始化（<clinit> 会执行）
// 2. 可以通过参数控制是否初始化：
//    Class.forName(name, initialize, classLoader)
// 3. 默认使用当前线程的类加载器

// ClassLoader.loadClass()：
// 1. 不会执行类的初始化（<clinit> 不执行）
// 2. 只是将类加载到 JVM 中但不初始化

// 典型场景：
// JDBC 驱动加载：
// JDK 6 之前：Class.forName("com.mysql.jdbc.Driver")
//   → 需要执行 Driver 的静态代码块注册到 DriverManager
// JDK 6+：使用 ServiceLoader，不需要 Class.forName

// 延迟加载（Lazy Loading）：
// ClassLoader.loadClass() 仅加载不初始化
// 适用于只在反射创建实例时才初始化的场景
```

### Q2：什么是双亲委派？为什么打破？

```java
// 双亲委派模型：
// 类加载器收到加载请求后，先委派给父加载器
// 父加载器无法加载时，子加载器才自己加载

// 为什么需要双亲委派？
// 1. 安全：防止核心 API 被替换（java.lang.String 不可被篡改）
// 2. 唯一：同一个类不会重复加载
// 3. 优先：核心库优先加载

// 为什么要打破？
// 1. SPI 机制：Bootstrap 加载的接口需要调用 Application 加载的实现
// 2. 容器隔离：Tomcat 需要为每个 WebApp 提供独立的类空间
// 3. 模块化：OSGi 需要网状委派而非树状
```

### Q3：一个类的唯一性如何确定？

```java
// 在 JVM 中，一个类由其全限定名（Fully Qualified Name）+ 类加载器共同决定
// 同一个 class 文件由不同的类加载器加载，视为不同的类

// 验证：
ClassLoader cl1 = new FileClassLoader("/tmp/classes");
ClassLoader cl2 = new FileClassLoader("/tmp/classes");

Class<?> clazz1 = cl1.loadClass("com.example.MyClass");
Class<?> clazz2 = cl2.loadClass("com.example.MyClass");

System.out.println(clazz1 == clazz2);        // false（不同的类加载器）
System.out.println(clazz1.equals(clazz2));    // false
System.out.println(clazz1.getClassLoader());  // cl1
System.out.println(clazz2.getClassLoader());  // cl2

// 这也意味着：
// clazz1.newInstance() instanceof MyClass  // ❌ ClassCastException
// 强制类型转换会失败（两个 MyClass 不是同一个类）
```

### Q6：编译期常量 vs 运行时常量？

```java
// 编译期常量（static final + 基本类型/String 字面量）：
//   → 编译期确定值，存储在引用类的常量池中
//   → 引用类不会触发目标类的初始化
//   → 修改目标类的常量值，引用类需要重新编译

// 运行时常量（new 创建的对象、运行时计算的值）：
//   → 运行时才能确定值
//   → 引用类会触发目标类的初始化
//   → 修改目标类的常量值，引用类无需重新编译

public class ConstDemo {
    static final int COMPILE_TIME = 100;           // 编译期常量
    static final String NAME = "hello";            // 编译期常量
    static final Integer WRAPPER = 100;            // 运行时常量（包装类）
    static final String RUNTIME = "a" + "b";       // 编译期常量（编译器优化）
    static final String RANDOM = String.valueOf(1); // 运行时常量
    static final long CURRENT = System.currentTimeMillis(); // 运行时常量
}
```
